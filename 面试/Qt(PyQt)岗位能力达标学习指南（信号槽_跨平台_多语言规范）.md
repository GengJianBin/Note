## 二、分模块系统化学习与实操达标方案

### 前置补充：Qt 与 PyQt 核心区别（必懂认知，规避开发误区）

很多开发者学习过程中容易混淆原生Qt（C\+\+）与PyQt/PySide，企业面试和实际开发中，需要清晰区分二者底层差异、优缺点及适用场景，以下为工程开发核心区别，贴合桌面开发岗位需求。

#### 1\. 语言与底层本质区别

- **Qt**：基于C\+\+的跨平台GUI开发框架，是**原生底层框架**，所有控件、信号槽、事件机制均由C\+\+原生实现，性能极强，无中间层损耗，是PyQt/PySide的底层依托。

- **PyQt**：是Qt C\+\+框架的**Python第三方绑定库**，由第三方公司Riverbank Software开发，本质是通过Python接口封装了Qt C\+\+的所有API，让开发者可用Python语法调用Qt底层能力。

- **补充PySide**：同为Qt的Python绑定库，由Qt官方维护，开源协议更宽松（LGPL），商业项目无版权风险，也是目前企业主流选型，和PyQt语法高度兼容。

#### 2\. 核心机制差异（信号槽/内存/线程）

- **内存管理差异**：原生Qt纯靠对象树父子机制自动回收内存，管控严谨；PyQt为C\+\+与Python双层内存管理，Python垃圾回收机制与Qt对象树叠加使用，极易出现**内存泄漏、控件残留、空对象调用**等问题，是PyQt开发核心避坑点。

- **线程机制差异（高频重难点）**：原生Qt与PyQt底层线程调度、UI独占逻辑一致，均遵循「UI线程独占原则，子线程禁止操作UI」，但**PyQt天生更容易出现资源抢占、对象销毁时序错乱、异步闪退问题**，核心根源四点：
        

    1. **双层对象生命周期割裂**：PyQt存在「Python上层对象 \+ C\+\+底层Qt对象」双层映射，两套生命周期独立。C\+\+ Qt线程、对象销毁时序由内核统一管控，严谨可控；Python GC异步、时机不确定，可能在线程任务执行、信号待回调时，提前销毁Python层对象，残留C\+\+底层逻辑继续执行，引发野对象调用、时序错乱。

    2. **GIL全局解释器锁调度缺陷**：Python多线程并非真正并行，依托时间片轮转并发，线程切换频繁且时机不可控。多子线程读写公共资源、全局变量时，极易无序抢占资源、数据覆盖，而C\+\+ Qt线程为系统内核精准调度，无此类问题。

    3. **信号队列时序紊乱**：跨线程QueuedConnection信号会存入主线程事件队列排队执行。C\+\+ Qt会随对象销毁同步清空队列任务；PyQt对象被GC回收后，事件队列仍残留未执行信号，后续调度时触发无效回调，造成闪退、报错。

    4. **开发者管控能力弱**：C\+\+可精准控制对象析构、线程退出、资源释放时机；PyQt无法干预GC回收逻辑，动态线程、定时器、异步任务极易出现生命周期不匹配问题。

#### 3\. 性能与场景适配差异

- **Qt\(C\+\+\)**：性能拉满，适合高性能、高并发、大型工业软件、嵌入式设备、实时性要求极高的桌面程序；编译体积小、运行速度快、资源占用低。

- **PyQt**：存在Python层调用损耗，性能低于原生Qt，不适合超高并发场景；开发效率极高、语法简洁、迭代速度快，适合快速开发中小型桌面工具、运维工具、可视化客户端、轻量级业务软件。

#### 4\. 商业授权与开源协议差异（工程规范重点）

- **PyQt**：采用**GPL协议**，商业闭源项目使用需购买商业授权，否则项目必须开源，存在版权风险。

- **PySide6/Qt官方**：采用**LGPL协议**，可免费用于商业闭源项目，仅需开源框架修改部分，无版权纠纷，是目前企业商业项目首选。

#### 5\. 开发与打包差异

- **编译打包**：原生Qt\(C\+\+\)编译产物体积小、运行稳定、依赖极少；PyQt需要打包Python解释器、大量依赖库，程序体积偏大，易出现依赖缺失、插件丢失、跨平台兼容问题。

- **开发效率**：PyQt无需编译、语法简洁、调试快速，开发效率远高于C\+\+ Qt；原生Qt编译繁琐、代码量大、开发周期长。

#### 6\. 岗位开发总结（面试高频话术）

Qt是C\+\+原生跨平台GUI框架，性能优异、稳定性强，适用于大型高性能软件；PyQt是Qt的Python封装库，开发高效、迭代迅速，适合轻量级快速落地项目。二者核心UI机制、信号槽原理、跨平台适配逻辑完全一致，仅在内存管理、性能、授权协议、打包部署存在差异。实际开发中优先使用PySide6规避版权风险，同时严格遵循Qt原生开发规范，解决Python层带来的内存、线程兼容问题。

- **内存管理 \& Qt对象树父子托管机制（Qt核心内存模型）**：吃透Qt独有的对象树托管机制，区分C\+\+ Qt与PyQt双层GC差异，彻底解决控件内存泄漏、野指针、残留报错问题，是中大型项目稳定运行的基础；

#### 2\. 深度专题：Qt元对象系统与MOC原理（面试深挖完整版）

MOC（Meta\-Object Compiler，元对象编译器）是Qt框架的核心基石，用于弥补**标准C\+\+无运行时反射、无动态类型识别、无动态成员绑定**的原生缺陷，是信号槽、动态属性、事件元信息体系的底层支撑。

##### 一、MOC底层工作原理

Qt的信号、槽、Q\_PROPERTY等均为Qt自定义扩展语法，标准C\+\+编译器无法识别。MOC作为预编译工具，会在项目编译前扫描所有带有 `Q_OBJECT` 宏的头文件，自动生成对应的moc\_xxx\.cpp元对象源码，源码包含信号实现、槽映射表、类型元数据、反射信息等，最终参与项目整体编译，实现运行时动态调度能力。

##### 二、MOC四大核心作用（逐点深度解析）

- **1\. 实现松耦合信号槽通信（核心作用）**：标准C\+\+函数调用为强耦合，调用方必须依赖被调用方的函数定义与类结构，扩展性极差。MOC预编译后会生成**信号\-槽字符串映射表**，记录所有信号、槽的名称、参数类型、函数内存地址。程序运行时，无需硬编码调用关系，仅通过字符串匹配即可动态绑定、触发回调，实现发送方与接收方完全解耦，互不依赖源码，支撑Qt模块化、插件化架构。

- **2\. 实现C\+\+运行时反射机制**：标准C\+\+仅支持编译期静态类型识别，运行时无法获取对象类名、成员函数、属性、枚举等信息。MOC生成的元对象数据，为每个QObject派生类封装一套完整运行时元数据，支持动态识别对象类型、遍历成员、调用未知函数，支撑Qt调试、插件加载、动态对象创建等核心能力。

- **3\. 支撑动态属性系统**：标准C\+\+类属性静态固定，编译后无法修改、新增。MOC解析 `Q_PROPERTY` 宏，自动生成动态属性读写接口与元信息，支持程序运行时动态增删、修改、读取对象属性，是QSS样式表、控件动态配置、可视化属性编辑的底层核心支撑。

- **4\. 提供事件与对象元信息识别能力**：MOC统一封装Qt对象的类型标识、事件元信息、父子层级数据。在事件分发、过滤器拦截、对象树托管、跨线程信号匹配过程中，Qt内核可通过元数据快速识别对象身份、判定事件归属，保障事件循环精准分发、内存托管安全、跨线程通信稳定。

##### 三、PyQt/PySide与原生Qt MOC核心差异

原生C\+\+ Qt需要手动配置MOC编译规则、生成moc源码文件；而PyQt/PySide底层已完全封装MOC逻辑，无需开发者手动预编译、生成文件。Python Qt对象初始化时，底层会自动完成元对象注册、信号槽映射、反射信息生成，开发语法更简洁，但**底层MOC核心机制、四大能力、调度逻辑与原生Qt完全一致**。

#### 3\. 深度专题：Qt对象树（父子托管机制）完整原理与PyQt实战避坑

Qt 区别于其它GUI框架最大的特色就是**对象树自动内存托管机制**，绝大多数Qt内存问题、闪退、残留控件报错，根源都是对该机制理解不透彻。该机制对所有 **QObject 派生类** 生效（所有控件、定时器、布局均生效）。

##### 一、对象树核心原理

Qt维护一棵**双向链表对象树**，开发者为控件指定父对象（parent）后，会建立父子托管关系：

- 子对象会被加入父对象的托管链表；

- 父对象生命周期全权管理子对象；

- **父对象销毁时，会自动递归销毁所有子对象**，无需手动 new/delete。

核心设计目标：**解决GUI控件海量创建销毁的内存管理复杂度，避免手动释放内存导致的野指针、内存泄漏。**

##### 二、父子关系建立规则

- 构造函数传参：`QPushButton(parent=self)` 直接绑定父子关系；

- 动态绑定：`obj.setParent(parent_widget)` 主动加入对象树；

- 布局添加控件：`layout.addWidget(btn)` 会**自动将布局所属窗口设置为控件父对象**，隐性建立托管关系。

##### 三、自动销毁执行顺序

1. 顶层窗口/父对象触发销毁；

2. 父对象析构函数遍历自身托管子对象列表；

3. 逐个销毁所有子对象，子对象再递归销毁自己的子对象；

4. 整棵分支对象树安全释放，无内存残留。

##### 四、C\+\+ Qt 与 PyQt/PySide 巨大差异（重点）

**1\. C\+\+ Qt**：完全依靠Qt对象树管理，开发者基本无需手动释放内存，规则严谨、极其稳定。

**2\. PyQt/PySide（高频坑点）**：存在**Python GC \+ Qt对象树 双层内存管理**，两套回收机制时序不统一，是PyQt独有难点：

- Python解释器的垃圾回收可能**提前回收Python对象**，但底层C\+\+ Qt对象还在运行；

- Qt事件队列残留信号/事件，触发已销毁对象调用，直接闪退；

- 局部变量控件无parent，函数结束后被GC回收，导致界面控件消失、莫名报错。

##### 五、PyQt开发必须遵守的工程规范

- **所有动态创建的控件必须绑定parent**，禁止裸创建局部控件；

- 长期驻留的控件、定时器、线程对象，必须设置父对象或绑定全局变量；

- 动态移除控件时，优先使用`obj.setParent(None)` 脱离对象树，再手动销毁；

- 窗口关闭销毁时，清空信号槽连接，防止残留信号触发野对象调用。

##### 六、常见报错场景（面试高频）

- **场景1**：函数内创建控件不指定parent，函数执行结束控件被Python GC回收，界面一闪而过消失；

- **场景2**：父窗口销毁，子控件指针未置空，后续操作残留控件导致闪退；

- **场景3**：子线程创建无父对象定时器，Qt对象树无法托管，内存持续泄漏。

##### 八、面试标准总结话术

Qt通过QObject对象树实现自动化内存托管，所有派生类对象通过parent建立父子关系，父对象销毁时会递归释放所有子对象，有效避免内存泄漏。在PyQt/PySide中存在Python GC与Qt对象树双层内存管理机制，容易出现对象提前回收、事件残留闪退等问题，开发中必须严格绑定控件父对象，规范动态控件生命周期管理，保证程序长期稳定运行。

#### 4\. Qt事件循环原理（面试核心必考 · 超详细原理完整版）

事件循环是**Qt GUI程序的运行内核**，是窗口不闪退、可交互、可刷新、信号槽可调度的底层基石。区别于普通Python脚本顺序执行完毕即退出，Qt GUI程序依靠事件循环实现「常驻进程、消息驱动、异步调度」。本节深度拆解事件循环**内核原理、执行机制、阻塞本质、线程限制、底层源码逻辑、PyQt独有特性**，覆盖面试和工程开发所有原理考点。

##### 一、事件循环本质定义

Qt事件循环本质是一个**基于操作系统消息队列的死循环消息调度器（QEventLoop）**。程序启动后主线程开启无限循环：不断**阻塞读取系统消息队列**、取出事件、逐层分发、执行回调；队列为空时休眠等待，有消息立即唤醒执行。**核心本质：GUI程序是事件驱动型程序，所有UI行为都由事件循环驱动。**

##### 二、底层内核完整执行流程（源码级原理）

Qt事件分发遵循固定调用链路：**系统消息队列 → QEventLoop → QApplication\.notify\(\) → 控件event\(\) → 细分事件函数 / 信号发射**

1. **操作系统投递事件**：Windows/Linux/macOS系统捕捉鼠标、键盘、窗口重绘、系统时钟、网络消息，写入当前进程的**系统消息队列**，队列先进先出。

2. **QEventLoop 轮询抓取**：主线程事件循环持续调用系统API读取队列，无事件时线程休眠（不占用CPU），有事件则取出。

3. **全局统一分发 notify\(\)**：所有事件最先进入 `QApplication::notify()` 全局分发函数，这是Qt事件最顶层入口，可全局拦截所有UI事件。

4. **目标控件 event\(\) 入口**：notify 将事件转发给目标控件的 `event(QEvent *e)` 虚函数，作为控件事件总入口。

5. **事件细分匹配执行**：event 内部通过事件类型判断，分发给对应具体事件函数：mousePressEvent / keyPressEvent / paintEvent / resizeEvent / closeEvent 等。

6. **上层信号触发**：原生控件的交互事件，会在事件函数内部自动 emit 对应信号（如 clicked、pressed），触发槽函数执行。

##### 三、事件循环四大核心底层作用（程序运行根本）

- **维持进程常驻**：普通脚本执行完立即退出，事件循环死循环阻塞主线程，让GUI进程常驻内存，等待用户操作。

- **驱动一切UI交互**：鼠标点击、悬浮、键盘输入、窗口拖动、大小缩放、界面重绘、弹窗显示，全部依赖事件循环调度。

- **支撑信号槽异步调度**：跨线程 QueuedConnection 信号不会立即执行，而是封装为 **MetaCall 事件** 投递到事件队列，由事件循环统一消费执行。

- **驱动定时器、系统回调、剪贴板、焦点变更**：所有系统级异步回调，全部依托主线程事件循环驱动。

##### 四、为什么子线程不能操作UI？（底层原理精讲）

高频面试核心考点，本质原因并非Qt限制，而是**线程与事件循环机制决定**：

- **只有主线程拥有QEventLoop**：子线程默认无事件循环、无消息队列、无法处理UI绘制与窗口事件。

- **所有窗口句柄、绘制上下文、系统UI资源归主线程独占**。

- 子线程操作UI时，产生的绘制事件、更新事件无循环调度，会导致：UI上下文错乱、内存踩踏、窗口花屏、程序硬崩溃。

**唯一安全跨线程UI更新方式**：子线程只做计算，通过**QueuedConnection信号槽**将数据抛回主线程，由主线程事件循环更新UI。

##### 五、事件循环阻塞原理（界面卡死根本原因）

Qt主线程事件循环是**单线程串行执行模型**：同一时间只能处理一个事件/任务，任务执行期间事件循环停止轮询，队列消息堆积，界面冻结。

###### 1\. 阻塞本质

主线程执行耗时代码（循环、IO、同步网络、sleep）→ **事件循环被抢占、停止调度** → 鼠标/重绘/点击事件无法处理 → 窗口白屏、未响应、卡死。

###### 2\. 常见阻塞场景

- 主线程 time\.sleep / 超大 for 循环 / 大量同步计算

- 主线程同步文件读写、同步数据库查询

- 主线程同步网络请求、阻塞式弹窗嵌套

###### 3\. processEvents\(\) 原理与利弊（深度解释）

`QApplication.processEvents()`：手动强制刷新并消费当前事件队列所有消息。

- **原理**：在阻塞耗时代码中，主动让出CPU，让事件循环临时执行一轮刷新UI。

- **弊端（工程禁止商用）**：极易造成**事件重入、递归嵌套、逻辑错乱、双击重复触发、栈溢出**，属于临时补丁，非正规解决方案。

- **企业标准解决方案**：所有耗时任务强制移入 QThread 子线程，异步回调UI。

##### 六、事件循环与信号槽的底层绑定关系

- **DirectConnection（直连）**：同步调用，发送信号的线程直接执行槽函数，不经过事件循环。

- **QueuedConnection（队列连接）**：异步事件，封装为元事件投递到接收者线程的事件循环，等待调度执行。

结论：**所有跨线程信号槽、异步UI更新，全部依赖主线程事件循环执行。**

##### 七、PyQt/PySide 独有事件循环问题（重点坑点）

C\+\+ Qt事件循环极其稳定，PyQt存在**Python解释器 \+ Qt原生事件循环 双调度模型**，产生独有问题：

- Python GC垃圾回收时机不可控，可能销毁Python层对象，但Qt底层C\+\+对象仍在事件队列残留事件；

- 导致：控件已销毁，但事件循环仍调度旧事件/信号，引发**野对象调用、闪退、报错**；

- 局部控件无parent、无全局引用，被GC回收，导致事件触发时对象不存在。

##### 八、app\.exec\(\) 底层真实原理

所有PyQt程序入口的 `app.exec()` 本质：**启动主线程QEventLoop，开启无限消息循环**。执行到这行代码时，主线程进入阻塞死循环，持续调度UI事件；关闭窗口后事件循环退出，程序结束。

```python
import sys
from PySide6.QtWidgets import QApplication, QWidget

app = QApplication(sys.argv)  # 初始化全局事件调度环境
win = QWidget()
win.show()

# 开启主线程事件循环，程序阻塞在此处，驱动所有UI逻辑
sys.exit(app.exec())

```

##### 九、面试极简总结话术

Qt事件循环是基于系统消息队列的单线程消息调度循环，是GUI程序常驻运行、UI交互、信号槽异步调度的底层核心。主线程独占事件循环，串行处理所有UI事件，主线程耗时代码会阻塞循环导致界面卡死。跨线程UI更新需通过队列信号槽交由主线程事件循环调度。PyQt存在双层内存与事件调度机制，容易出现残留事件闪退问题，开发中必须严格遵循主线程UI独占、耗时任务子线程异步的开发规范。

#### 5\. 信号槽机制 vs 事件机制（适用场景核心差异 · 面试必考）

二者都是Qt核心通信与交互机制，底层互通但**定位层级、使用场景、开发粒度完全不同**，工程开发必须按需选用。

##### 1\. 核心本质区别

- **事件机制（QEvent）**：**系统底层驱动、UI内核级机制**，由操作系统/Qt内核抛出，偏向「界面物理交互、绘制、状态变更」，是Qt UI最底层的支撑。

- **信号槽机制（Signal/Slot）**：**框架上层封装、业务解耦机制**，基于元对象系统实现，偏向「业务逻辑通信、模块间解耦回调」，是对事件机制的高层封装。

##### 2\. 精准适用场景（开发选型标准）

**优先使用【事件机制/重写事件】场景：**

- 需要**自定义UI交互行为**：自定义控件绘制、自定义鼠标/键盘/滚轮逻辑；

- 需要**拦截、禁用、篡改原生控件默认交互**（禁止按钮点击、拦截输入框按键）；

- 需要**全局监控UI事件**、统一事件过滤、权限拦截；

- 需要精细绘制控制：重写paintEvent实现自定义样式、动态绘制。

**优先使用【信号槽】场景：**

- **业务逻辑解耦**：界面与业务逻辑分离、模块与模块通信；

- 常规UI交互回调：按钮点击、输入框内容改变、下拉框选中；

- **跨线程异步通信**：子线程结果回传UI（信号槽是Qt唯一安全跨线程UI通信方式）；

- 一对多、多对一广播通知：一个信号触发多个业务逻辑。

##### 3\. 层级关系（底层流转逻辑）

用户点击按钮 → 操作系统产生鼠标点击事件 → Qt事件循环接收并分发 → 按钮mousePressEvent触发 → Qt内部**手动emit clicked信号** → 绑定的槽函数执行。**结论：信号是事件的上层产物，事件是信号的底层来源。**

#### 6\. 事件过滤器（installEventFilter）完整原理、用法与注意事项

事件过滤器是Qt中**全局拦截、监控、篡改任意控件事件**的高阶技术，无需继承重写控件，即可统一处理多个控件的事件，是企业项目统一风控、输入拦截、权限控制的核心方案。

##### 1\. 底层原理

- Qt所有事件在到达目标控件的 `event()` 函数**之前**，会先经过**事件过滤器**校验；

- 通过 `installEventFilter()` 给目标控件安装过滤器，监听者接管事件预处理权限；

- 执行优先级：**事件过滤器 \> 控件自身event\(\) \> 具体细分事件函数**；

- 返回 `True`：拦截事件，事件终止，不再向下传递；返回 `False`：放行事件，控件正常响应。

##### 2\. 核心优势

- 无需继承原生控件，**非侵入式**修改控件行为；

- 一个过滤器可同时监听/拦截**多个不同控件**事件，代码高度复用；

- 统一全局风控：统一拦截非法输入、禁用快捷键、拦截弹窗、屏蔽无效点击。

##### 3\. 完整可运行代码示例（PySide6/PyQt通用）

案例：全局拦截所有输入框空格、禁止按钮右键点击、监控键盘按键

```python
import sys
from PySide6.QtWidgets import QApplication, QWidget, QLineEdit, QPushButton, QVBoxLayout
from PySide6.QtCore import Qt, QEvent

class EventFilterDemo(QWidget):
    def __init__(self):
        super().__init__()
        self.setWindowTitle("事件过滤器 原理与示例")
        self.resize(400, 200)
        self.init_ui()

    def init_ui(self):
        self.edit = QLineEdit("禁止输入空格")
        self.btn = QPushButton("禁止右键点击")

        layout = QVBoxLayout(self)
        layout.addWidget(self.edit)
        layout.addWidget(self.btn)

        # 给目标控件安装事件过滤器
        self.edit.installEventFilter(self)
        self.btn.installEventFilter(self)

    # 事件过滤器核心函数（重写父类方法）
    def eventFilter(self, watched, event):
        # 1. 拦截输入框：禁止空格输入
        if watched == self.edit and event.type() == QEvent.KeyPress:
            if event.key() == Qt.Key_Space:
                # 拦截事件，不向下传递
                return True

        # 2. 拦截按钮：禁止鼠标右键
        if watched == self.btn and event.type() == QEvent.MouseButtonPress:
            if event.button() == Qt.RightButton:
                return True

        # 其余事件全部放行
        return super().eventFilter(watched, event)

if __name__ == "__main__":
    app = QApplication(sys.argv)
    win = EventFilterDemo()
    win.show()
    sys.exit(app.exec())

```

##### 4\. 关键使用注意事项（工程避坑）

- **监听者对象生命周期必须长于被监听控件**：如果过滤器所属对象提前销毁，控件触发事件时会程序闪退；

- **禁止无脑return True**：会拦截所有鼠标、键盘、绘制事件，导致控件彻底失效、黑屏无响应；

- **精准匹配控件与事件类型**：多控件监听时必须通过 `watched` 区分来源，否则全局事件错乱；

- **移除过滤器**：动态控件销毁前，建议执行 `obj.removeEventFilter(self)`，避免残留监听导致内存异常；

- **PyQt独有坑**：Python垃圾回收可能误回收过滤器对象，导致事件崩溃，长期窗口建议绑定全局变量；

- **过滤器层级叠加**：多个过滤器可叠加监听，安装顺序决定执行顺序，避免多层拦截冲突。

#### 7\. Qt Model/View（MVC改良版）原理与实战示例

普通开发者直接操作控件写入数据，耦合度极高、无法复用、数据量大时卡顿；企业级Qt开发强制使用Model/View架构，实现**数据与视图彻底分离**。Qt对经典MVC做了精简改良，去掉独立Controller层，由View自身完成交互控制，是Qt大批量数据展示的标准化方案。

##### 一、Model/View三层核心架构

- **Model 模型（数据层）**：负责存储、提供、更新原始数据，不关心界面展示。对外提供统一数据接口，支持数据增删改查、刷新通知。对应类：`QAbstractItemModel`、`QStandardItemModel`、`QFileSystemModel`等。

- **View 视图（展示层）**：负责界面渲染、用户交互，不持有原始数据。仅从Model获取数据展示。对应类：`QTableView`、`QListView`、`QTreeView`。

- **Delegate 委托（编辑层）**：负责单元格/条目自定义绘制、自定义编辑控件（下拉框、复选框、输入框），实现UI个性化定制。

##### 二、核心优势（为什么要用MVC）

- 数据与UI解耦：一份Model数据可同时给Table/List/Tree多个视图复用；

- 高性能渲染：只绘制可视区域数据，万级数据不卡顿；

- 可维护性强：数据逻辑、界面展示、样式绘制分层独立；

- 自动刷新：Model数据变更可通过信号自动更新View，无需手动刷新控件。

##### 三、PySide6/PyQt可直接运行 MVC实战示例（表格数据展示）

场景：使用QStandardItemModel \+ QTableView实现解耦式表格数据展示，纯规范写法，企业项目通用模板。

```python
import sys
from PySide6.QtWidgets import QApplication, QWidget, QTableView, QVBoxLayout
from PySide6.QtGui import QStandardItemModel, QStandardItem

class MvcDemoWindow(QWidget):
    def __init__(self):
        super().__init__()
        self.setWindowTitle("Qt MVC(Model/View) 示例")
        self.resize(600, 400)
        self.init_ui()
        self.init_data()

    def init_ui(self):
        # View层：只负责展示，不存数据
        self.table_view = QTableView()
        layout = QVBoxLayout(self)
        layout.addWidget(self.table_view)

    def init_data(self):
        # Model层：只负责数据，不关心UI
        self.model = QStandardItemModel()
        # 设置表头
        self.model.setHorizontalHeaderLabels(["姓名", "年龄", "岗位"])
        # 模拟业务数据
        data_list = [
            ["张三", "24", "Qt开发"],
            ["李四", "26", "Python开发"],
            ["王五", "25", "桌面开发"]
        ]
        # 数据载入Model
        for row, data in enumerate(data_list):
            for col, text in enumerate(data):
                item = QStandardItem(text)
                self.model.setItem(row, col, item)

        # 绑定Model与View
        self.table_view.setModel(self.model)

if __name__ == "__main__":
    app = QApplication(sys.argv)
    win = MvcDemoWindow()
    win.show()
    sys.exit(app.exec())

```

##### 四、关键机制说明（面试加分点）

- 数据全部存在Model中，QTableView只是「画布」，不保存任何数据；

- 修改Model数据：`setItem()`后视图**自动刷新**，无需手动更新UI；

- 如需自定义单元格样式、编辑控件，重写`QStyledItemDelegate`即可，不改动数据逻辑；

- 支持海量数据：相比QTableWidget逐条addRow，ModelView是批量映射，性能碾压。

##### 五、QTableWidget 与 QTableView 核心区别（避坑\&面试）

- **QTableWidget**：自带Model，数据UI耦合，适合极少量静态数据，项目不推荐；

- **QTableView**：纯视图，依赖外部Model，数据视图分离，适合所有正式项目、海量数据、动态更新场景。
